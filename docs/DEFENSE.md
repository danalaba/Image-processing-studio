## Підготовка до показу

У VS Code відкрийте корінь репозиторію. Підготуйте три невеликі фото JPG/PNG/WebP,
демоакаунт і вільне місце в історії: до 20 задач, дві незавершені одночасно.
На Mac кілька фото вибираються через ⌘ + клік або Shift для діапазону.

Docker Desktop має працювати. У першому терміналі:

```sh
docker compose up --build --remove-orphans
```

Залиште його відкритим. У другому терміналі:

```sh
docker compose ps
```

Мають бути `nginx`, `api-1`, `api-2`, `db`, `redis`, `worker-1`, `worker-2`,
`scheduler`. Для API/Nginx/БД/Redis є healthchecks; workers перевіряються виконанням
задач, а не самим написом «running».

Відкрийте `http://localhost:8000` у Safari. Порт PostgreSQL 5434 у вашій локальній
копії можна зберегти: усередині Docker обидва API використовують `db:5432`.
Для HTTP-демонстрації Python на Mac не потрібен. Для автоматичної перевірки
workers заздалегідь підготуйте venv за [командами](COMMANDS.md#підготовка-python-для-автоперевірок).

## Послідовність

| Час | Що показати | Що сказати / очікувати |
|---|---|---|
| 0:00–0:45 | Назва, задача проєкту | Студія обмеженої пакетної обробки фото з обліковими записами й історією |
| 0:45–1:30 | Схема архітектури | Nginx → два API; Redis → два workers; PostgreSQL — спільний стан і файли |
| 1:30–2:15 | Вхід і HTTP-балансування | Сесія зберігається незалежно від API, який відповідає |
| 2:15–3:30 | Пакет із трьох фото → ZIP | 202 Accepted, прогрес, три PNG усередині ZIP, збереження в історії |
| 3:30–4:30 | Автоперевірка workers | Два різні job ID та два різні worker ID |
| 4:30–6:00 | Черга та скасування | Зупинити workers, створити QUEUED job, скасувати, відновити workers |
| 6:00–7:15 | Відмова одного API | Зупинити api-2, сайт відповідає через api-1, відновити api-2 |
| 7:15–8:15 | Історія після виходу/входу | Результати лишилися; завантажити старий ZIP повторно |
| 8:15–9:00 | Обмеження та висновок | Обмежені файли/пікселі/задачі/час; назвати реалізовані й майбутні можливості |

## 1. HTTP-балансування

Натисніть «Перевірити зв’язок» кілька разів. Поле «Сервер» показує `api-1` і `api-2`.
Для наочних HTTP-відповідей у другому терміналі Mac:

```sh
for i in {1..8}
do
  curl --fail --silent --show-error http://localhost:8000/api/health
  printf '\n'
done
```

Очікується JSON зі `status: ok` і обома значеннями `instance_id`. Строге чергування
та рівно 50/50 не є умовою: є також polling, статика та healthchecks.

Фраза для захисту:

> Це відповіді двох реальних API через один вхід Nginx. Сесії та історія спільні,
> тому прив’язка користувача до одного сервера не потрібна.

За наявності venv повніша перевірка:

```sh
.venv/bin/python scripts/check_load_balancing.py
```

Скрипт перевіряє не лише ідентифікатори, а й спільну сесію, читання результату,
ownership і відкликання токена на обох API.

## 2. Пакет і збереження результатів

1. Увійдіть та виберіть три фото через ⌘ + клік.
2. Укажіть рамку 200×200 й натисніть «Обробити пакет».
3. Покажіть stage, відсоток і кількість оброблених фото.
4. Дочекайтеся `COMPLETED`, завантажте ZIP і відкрийте його у Finder.
5. Покажіть три PNG та рядок цієї задачі в історії.

Safari може автоматично розпакувати ZIP: тоді в «Завантаженнях» буде папка з PNG.

200×200 — обмежувальна рамка. Для прямокутного фото результат може бути,
наприклад, 200×100 або 111×200: пропорції зберігаються. Маленькі фото не збільшуються.
На малих файлах проміжні етапи можуть промайнути між двома polling-запитами.

> API швидко повертає 202 і номер задачі. Обчислення виконує окремий Celery worker,
> а браузер читає стан із PostgreSQL через API.

## 3. Доказ роботи двох workers

Із підготовленим venv:

```sh
.venv/bin/python scripts/check_queue.py --batch --require-two-workers
```

Очікуваний зміст виводу, ідентифікатори будуть ваші:

```text
job=<UUID A> status=COMPLETED progress=100 files=2 worker=worker-1@...
job=<UUID B> status=COMPLETED progress=100 files=2 worker=worker-2@...
Queue smoke passed: ...
```

Скрипт створює тестовий акаунт і два пакети, перевіряє ZIP/PNG, видаляє свої задачі
та виходить. Акаунт лишається без результатів. Паролі й токени не друкуються.

> Це окрема перевірка обчислювального рівня: два різні пакети виконалися на двох
> workers. Один пакет не розбивається між workers; фото в ньому обробляються послідовно.

У `Task studio.resize[UUID]` журналу Celery UUID — це Celery task ID. Він не
зобов’язаний збігатися з application job ID. Для доказу зв’язку job ↔ worker
використовуйте метадані й вивід скрипта вище.

## 4. Черга та скасування без гонки зі швидким фото

У другому терміналі, залишаючи перший із Compose відкритим:

```sh
docker compose stop worker-1 worker-2
```

На сайті створіть нову задачу: вона лишається `QUEUED`, сайт і історія доступні.
Натисніть «Скасувати задачу»: очікується `CANCELLED` та 0%, якщо обробка не почалася.
Поверніть workers одразу після показу:

```sh
docker compose start worker-1 worker-2
```

> У черзі скасування відбувається одразу. Для активної задачі спершу буде
> CANCELLING; worker зупиниться на межі етапів або фото. Один виклик Pillow не
> переривається миттєво. Завершена раніше задача зберігає статус COMPLETED.

## 5. Відмова одного API

```sh
docker compose stop api-2
```

На сайті натисніть «Перевірити зв’язок»: має відповідати `api-1`. Покажіть історію
та завантаження результату. Потім обов’язково поверніть другий API:

```sh
docker compose start api-2
```

Дайте йому кілька секунд на запуск та повторіть HTTP-перевірку. За потреби
подивіться `docker compose ps` і `docker compose logs --tail=20 api-2 nginx`.

> Nginx виключає недоступний upstream і продовжує обслуговування через інший API.
> Це перевірка відмови одного API. Сам Nginx, PostgreSQL і Redis тут по одному.

Після всіх демонстрацій можна відновити повний стек:

```sh
docker compose up -d --wait
```

## Відповідність вимогам

| Вимога | Що показати | Де перевіряється |
|---|---|---|
| Межа роботи однієї задачі | Файли, байти, пікселі, рамка, час, кількість задач | [limits.py](../backend/app/limits.py), [jobs.py](../backend/app/jobs.py), [tasks.py](../backend/app/tasks.py) |
| Прогрес | Stage, відсоток, оброблено N із M | [tasks.py](../backend/app/tasks.py), [app.js](../frontend/app.js) |
| Задачі, історія, результати, скасування | Пакет → ZIP, повторний вхід, CANCELLED | [jobs.py](../backend/app/jobs.py), [database.py](../backend/app/database.py) |
| Автентифікація та ownership | Вхід; чужі job/result повертають 404 | [auth.py](../backend/app/auth.py), [test_accounts_jobs.py](../backend/tests/test_accounts_jobs.py) |
| Два API й HTTP-балансування | Два instance ID через Nginx | [check_load_balancing.py](../scripts/check_load_balancing.py) |
| Кілька обчислювальних workers | Два job ID з різними worker ID | [check_queue.py](../scripts/check_queue.py) |
| Черга при зайнятих workers | QUEUED під час зупинки workers | Redis/Celery, [test_queue.py](../backend/tests/test_queue.py) |

Показ помилки у браузері демонструє UX-перевірку. Щоб підтвердити саме backend-ліміт,
відкрийте відповідні API-тести: вони надсилають запити напряму, обходячи JavaScript.
Не називайте реалізованими ETA, autoscaling, admin-панель або HTTPS — це наступні покращення.
