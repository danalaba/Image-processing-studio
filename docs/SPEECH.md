# Короткий виступ і відповіді на запитання

## Вступ на 2–3 хвилини

> Мій проєкт — Image Processing Studio, вебзастосунок для пакетної обробки
> зображень. Користувач входить у свій обліковий запис, вибирає до десяти фото,
> задає рамку зміни розміру та створює фонову задачу. Для одного фото результатом
> є PNG, для кількох — ZIP із PNG. Історія та результати зберігаються після виходу.
>
> Система має два окремі рівні розподілу роботи. На HTTP-рівні Nginx передає
> запити двом екземплярам FastAPI. Кожен API повертає власний instance ID.
> Сесії, задачі та файли зберігаються в одній PostgreSQL, тому будь-який API може
> обслуговувати того самого користувача.
>
> Для обчислень використовується Celery із Redis як брокером. API спочатку
> зберігає задачу, а потім передає її UUID у чергу й повертає HTTP 202. Два workers
> можуть одночасно виконувати різні задачі. Один пакет виконує один worker,
> послідовно обробляючи фото бібліотекою Pillow.
>
> Під час роботи користувач бачить етап, умовний відсоток і кількість оброблених
> фото. Стан зберігається в базі, браузер оновлює його polling-запитами.
> Задачу можна скасувати: у черзі — одразу, під час виконання — між етапами.
>
> Backend обмежує кількість файлів, їхній розмір, пікселі, кількість задач і час
> обробки. Ці перевірки не залежать від JavaScript. Паролі хешуються Argon2id,
> а доступ до кожної задачі й результату перевіряється за власником.
>
> На демонстрації я окремо покажу два API, два workers, створення ZIP, чергу,
> скасування й доступність сайту при зупинці одного API. HTTPS, приблизний час
> очікування, autoscaling та admin-монітор залишаються напрямами подальшої роботи.

## Типові запитання

**Чим балансування Nginx відрізняється від розподілу Celery?**

Nginx вибирає API для HTTP-запиту. Celery workers отримують окремі jobs із Redis.
Докази різні: `instance_id` для HTTP, `worker_id` у метаданих job для обчислень.

**Один пакет виконується на двох workers?**

Ні. Поточний worker обробляє всі фото одного пакета послідовно. Паралельність
демонструється двома різними jobs на двох workers.

**Чому два API бачать того самого користувача й результат?**

Вони користуються спільною PostgreSQL. Сесії, owner ID, історія та бінарні
результати не зберігаються в локальному Python-списку чи в одному API-контейнері.

**Де зберігаються фото?**

Зараз у PostgreSQL: входи — `BYTEA[]`, старі одиночні входи та результати — `BYTEA`.
Це просте спільне сховище для демонстрації. Для більших обсягів наступний крок —
об'єктне сховище з метаданими в PostgreSQL.

**Що лежить у Redis?**

Повідомлення Celery з UUID задачі та службові повідомлення. Фото й результати
зберігаються в PostgreSQL. Для Redis увімкнено AOF та іменований том.

**Чи є гарантія exactly-once?**

Черга може доставити повідомлення повторно. Worker атомарно отримує claim лише
для `QUEUED` job, тому дубль не починає другу обробку того самого job. Водночас
повторне HTTP-надсилання створює новий job: окремого idempotency key запиту немає.

**Що буде при недоступному Redis?**

Валідний job спочатку зберігається в PostgreSQL. Якщо публікація не вдалася,
він лишається `QUEUED`. Коли Redis, scheduler і workers доступні, службова задача
повторно публікує UUID. Це durable outbox.

**Що робить scheduler?**

Celery beat кожні 5 с ставить службову задачу в Redis. Її виконує доступний worker:
повторно відправляє непочаті jobs і позначає застарілі активні jobs термінальними.

**Скасування миттєве?**

Для черги — одразу. Під час обробки перевірка виконується між фото та етапами.
Поточна операція Pillow може ще працювати; стан тоді `CANCELLING`. Якщо job уже
завершився до запиту скасування, результат зберігається.

**Прогрес — це точна кількість оброблених пікселів?**

Ні, це відсотки за етапами з масштабуванням на кількість фото в пакеті.
Polling може пропускати швидкі проміжні стани. Окремо показується кількість готових фото.

**Що станеться після аварії worker?**

Якщо активний job старший за 90 с, періодична перевірка позначить його `FAILED`
або `CANCELLED`. Для перевірки теж потрібен доступний worker. Початий job
автоматично заново не обчислюється; користувач може створити новий.

**Чи вся система відмовостійка?**

Перевірено продовження роботи при зупинці одного API. Nginx, PostgreSQL і Redis
поки по одному, тому повну відмовостійкість кластера я не заявляю.

**Як перевіряється доступ до чужих файлів?**

API знаходить job одночасно за UUID та user ID із сесії. Для чужого job
метадані, результат, скасування й видалення повертають 404. Токени зберігаються
в БД як SHA-256-хеші; паролі — Argon2id.

**Чи достатньо обмеження в браузері?**

Ні. Ті самі межі перевіряє backend до черги; worker додатково контролює вихідний
розмір і час. API-тести обходять JavaScript і перевіряють відповіді сервера.

**Що саме покривають 59 тестів?**

Auth, ownership, формати й обмеження зображень, ZIP, історію, скасування, claim,
outbox і recovery на PostgreSQL. Redis publish у цій suite підмінений. Реальний
Nginx і реальні workers перевіряються окремими smoke-скриптами та браузерним сценарієм.

**Що ще не реалізовано?**

HTTPS, ETA, autoscaling, admin-монітор і автоматичне очищення старих результатів.
Зараз доступні resize та видача PNG/ZIP; інші операції обробки — наступні покращення.
