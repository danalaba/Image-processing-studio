# Image Processing Studio

Навчальна студія обробки фото: акаунти, особиста історія, фонова зміна розміру,
прогрес і скасування. FastAPI приймає запит, PostgreSQL зберігає задачу та файли,
Redis передає ID задачі, а два Celery workers виконують обробку Pillow.

## Запуск на Mac / у VS Code

Потрібен запущений Docker Desktop. Відкрийте термінал VS Code в корені проєкту.
Один раз створіть `.env` із випадковим паролем PostgreSQL. Команда не перезаписує
наявний файл — якщо `.env` уже є, пропустіть її:

```sh
python3 -c 'import os,secrets; f=os.fdopen(os.open(".env",os.O_WRONLY|os.O_CREAT|os.O_EXCL,0o600),"w"); f.write("POSTGRES_PASSWORD="+secrets.token_hex(32)+"\n"); f.close()'
docker compose up --build
```

Відкрийте `http://localhost:8000` **в адресному рядку браузера**. Створіть акаунт,
оберіть одне фото та рамку. Після надсилання задача з'явиться в історії, а статус
оновлюватиметься автоматично. Можна додати ще одну задачу, поки перша виконується.
Після завершення доступні перегляд і повторне завантаження PNG.

Порт API — 8000, локальний порт PostgreSQL — 5433. Якщо 5433 зайнятий, змініть
лише мапінг `db.ports` у `compose.yaml` на `"127.0.0.1:5434:5432"`. Зв'язок між
контейнерами від цього не змінюється. Redis за замовчуванням не має порту на Mac.

Зупинка — Ctrl+C, потім `docker compose down`. **Не використовуйте `down -v`**:
це видалить томи з акаунтами, історією, результатами та Redis. Існуючий пароль
PostgreSQL не змінюється від редагування `.env`; зберігайте файл або виконуйте
узгоджену ротацію пароля в самій базі. `.env` не потрапляє у Git і Docker-образ.

### Оновлення попередньої версії

Зупиніть запущений Compose через Ctrl+C. Якщо у вас локально змінений лише порт
у `compose.yaml`, тимчасово збережіть саме цю зміну перед оновленням:

```sh
git stash push -m "Local Docker port" -- compose.yaml
git pull --ff-only
git stash pop
docker compose up --build
```

Якщо локальних змін немає, достатньо `git pull --ff-only` і `docker compose up --build`.
Міграція схеми виконується автоматично в транзакції під блокуванням: існуючі
акаунти, сесії та завершені результати зберігаються. Незавершені синхронні задачі
попереднього етапу позначаються невдалими — їх можна створити повторно.

## Як працює фонова обробка

```text
Браузер → FastAPI → PostgreSQL (метадані, вхідне фото, результат)
                    ↓ ID задачі
                  Redis → Celery worker-1 / worker-2 → PostgreSQL
Браузер ← polling стану й прогресу через API
```

`POST /api/jobs` перевіряє файл і параметри, зберігає його та повертає
**HTTP 202 із JSON задачі**, поки Pillow працює окремо. Старий шлях
`POST /api/images/resize` залишено як deprecated-аліас із такою самою відповіддю
202; він більше не повертає PNG одразу. Результат завантажується окремим запитом.

Стани: `QUEUED` → `RUNNING` → `COMPLETED` / `FAILED`.
Скасування в черзі одразу дає `CANCELLED`. Для активної задачі — `CANCELLING`,
потім `CANCELLED` на найближчій межі етапів. Поточний виклик Pillow не переривається
миттєво. Якщо завершення випередило запит скасування, зберігається `COMPLETED`.

Прогрес — **умовні відсотки за етапами**, а не вимірювання оброблених пікселів:
перевірка 5–10%, читання 20%, орієнтація 45%, resize 60%, PNG 85%, збереження 95%,
готово 100%. Браузер опитує стан кожні 1,5 с; швидкі етапи можуть не встигнути
відобразитися. Прогрес і stage зберігаються в PostgreSQL та доступні після входу.

Кожен worker має concurrency=1, prefetch=1. Два workers можуть обробляти дві
**окремі** задачі; одна задача не ділиться між ними. У метаданих є `worker_id`.
HTTP-балансування Nginx і два API-сервери ще не реалізовані.

### Надійність і межі роботи

- PostgreSQL — джерело істини. Redis отримує лише UUID, а не фото, паролі чи результати.
- Задача спочатку комітиться в БД. За недоступності Redis залишається `QUEUED`.
  Scheduler (Celery beat) кожні 5 с запускає повторну відправку. Відправлена задача,
  яка не почала виконання за 15 с, може бути надіслана повторно. Атомарний claim
  дозволяє виконати її лише одному worker; дублікати і скасовані задачі пропускаються.
- Redis має AOF і окремий том. Durable outbox у БД дозволяє відновити непочаті
  задачі навіть після втрати повідомлення в Redis. Для цього потрібні Redis,
  scheduler і хоча б один працюючий worker.
- Soft time limit Celery — 50 с, hard limit — 60 с. Після аварійного завершення
  worker активна задача віком понад 90 с позначається `FAILED` або `CANCELLED`
  періодичною перевіркою. Автоматичного повторного виконання вже початої задачі
  немає. Перевірка може затриматися, якщо всі workers зайняті чи недоступні.
- Вхідні байти видаляються при завершенні, помилці, скасуванні або відновленні
  аварійної задачі. Завершені PNG зберігаються до видалення користувачем.

## Обмеження

Одне JPG, PNG або WebP до 10 MiB, 12 млн пікселів і 12000 px на сторону;
анімація не приймається. Рамка — 1–4096 px, пропорції зберігаються, маленькі
фото не збільшуються. Результат — PNG до 20 MiB.

На користувача — до **20 збережених** задач і **двох незавершених**
(`QUEUED`/`RUNNING`/`CANCELLING`). Невдалі й скасовані теж займають місце в історії;
їх можна видаляти. Загальна черга — до 100 незавершених задач. Admission використовує
блокування в PostgreSQL, тому паралельні API-запити не обходять ліміти.

## API та автентифікація

- `POST /api/auth/register`, `/api/auth/login`: JSON `username`, `password` → bearer-токен.
- `GET /api/auth/me`, `POST /api/auth/logout`: поточний акаунт / відкликання сесії.
- `POST /api/jobs`: multipart `file`, `width`, `height` → 202 JSON із ID.
- `GET /api/jobs`, `GET /api/jobs/{id}`: власна історія / стан, stage, progress, worker_id.
- `POST /api/jobs/{id}/cancel`: запит скасування власної задачі, повторний виклик безпечний.
- `GET /api/jobs/{id}/result`: PNG після `COMPLETED`; інакше 409.
- `DELETE /api/jobs/{id}`: власна термінальна задача разом із результатом.
- `GET /api/health`: API та PostgreSQL; не є перевіркою виконання Celery.
- `GET /docs`: опис маршрутів.

Захищені маршрути вимагають `Authorization: Bearer <access_token>`. Чужі задачі
повертають 404. Паролі — Argon2id; сесії — випадкові токени з SHA-256-хешами в БД,
24 години, до п'яти на акаунт. Браузер використовує `sessionStorage`. Імена:
3–40 латинських літер, цифр, `_`/`-`, без урахування регістру; паролі: 10–128 символів.
Вхід/реєстрація обмежені 30 запитами/хв на IP і 10/хв на ім'я. Перед публічним
розгортанням потрібен HTTPS; для Nginx потрібно налаштувати довірені proxy IP.

## Розробка з Python 3.12

Рекомендований спосіб демонстрації — весь Compose. Для роботи з Python напряму
встановіть залежності та відкрийте локальний Redis лише через dev-override:

```sh
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements-dev.txt
docker compose -f compose.yaml -f compose.dev.yaml up -d --wait db redis
```

У кожному потрібному терміналі з кореня проєкту активуйте venv і налаштування:

```sh
source .venv/bin/activate
set -a
source .env
set +a
export DATABASE_URL="postgresql://studio:${POSTGRES_PASSWORD}@127.0.0.1:5433/studio"
export CELERY_BROKER_URL="redis://127.0.0.1:6380/0"
```

Якщо ваш локальний порт БД — 5434, використайте його в `DATABASE_URL`.
Запустіть окремо в трьох терміналах:

```sh
# Термінал 1
python -m uvicorn app.main:app --app-dir backend --reload --host 127.0.0.1 --port 8000
# Термінал 2 (один worker для розробки)
PYTHONPATH=backend celery -A app.queue:celery worker --loglevel=INFO --concurrency=1 --hostname=local-1@%h
# Термінал 3
PYTHONPATH=backend celery -A app.queue:celery beat --loglevel=INFO --schedule=/tmp/studio-celerybeat
```

Не запускайте контейнер API та локальний Uvicorn одночасно на порту 8000.
Scheduler має бути один на брокер. `DATABASE_URL` обов'язковий; міграція запускається
API і workers автоматично. Схема версіонується в `schema_migrations`.
Вхід і результати поки зберігаються у `BYTEA`, спільному для API та workers;
файлове/об'єктне сховище й автоматичне очищення залишаються наступними покращеннями.

## Тести та демонстрація на захисті

Інтеграційні тести використовують окрему PostgreSQL. Один раз створіть базу:

```sh
docker compose exec db createdb -U studio studio_test
```

З активованим venv, завантаженим `.env` і запущеною БД:

```sh
export TEST_DATABASE_URL="postgresql://studio:${POSTGRES_PASSWORD}@127.0.0.1:5433/studio_test"
PYTHONPATH=backend python -m unittest discover -s backend/tests -v
```

**48 тестів** перевіряють auth, зображення, історію, ліміти, HTTP 202, прогрес,
скасування, idempotent claim, outbox і відновлення аварійних задач. Redis-публікація
в цих тестах підмінена, а обробник викликається в процесі тестів. Вони серійно
очищають лише явно задану базу з суфіксом `_test`; дані `studio` не видаляються.
Не підключайте реальних workers до цієї тестової БД.

Для **реальної** черги, запущених Redis, scheduler та обох workers:

```sh
python scripts/check_queue.py --require-two-workers
```

Скрипт створює тестовий акаунт, надсилає два фото, перевіряє результати і виводить
job ID та worker ID. Потім видаляє власні задачі й виходить; тестовий акаунт
залишається без результатів. Два різні `worker_id` — доказ розподілу фонових задач,
не HTTP-балансування. Дочекайтеся готовності обох workers перед перевіркою.

Щоб показати чергу та скасування на екрані:

```sh
docker compose stop worker-1 worker-2
# У браузері створіть задачу: вона лишиться QUEUED, API/історія продовжують працювати.
# Натисніть «Скасувати» — статус стане CANCELLED.
docker compose start worker-1 worker-2
```

Для перегляду worker-журналів:

```sh
docker compose logs --tail=50 worker-1 worker-2
```

## Хмарне середовище з TLS-проксі

Dockerfile підтримує необов'язковий BuildKit secret `proxy_ca`. Приклад збірки:

```sh
docker build --secret id=proxy_ca,src=/etc/ssl/certs/ca-certificates.crt -t image-processing-studio-app .
docker compose up -d --no-build --wait
```

Для Compose build секрет потрібно передати через зовнішній override-конфіг.
Не вимикайте перевірку TLS. Локальні WOFF2-шрифти та їхні OFL-ліцензії знаходяться
в `frontend/fonts`; палітра оливковий / navy / бургунді описана в `DESIGN_SYSTEM.md`.

Наступні кроки: пакет фото й ZIP, потім Nginx, два API-сервери та окрема перевірка
HTTP-балансування. Приблизний час очікування, autoscaling та admin-монітор поки не реалізовані.
