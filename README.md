# Image Processing Studio

Навчальний вебзастосунок: реєстрація та вхід, завантаження одного JPG, PNG або
WebP, зміна розміру зі збереженням пропорцій і результат у PNG. FastAPI обслуговує
API та інтерфейс, Pillow обробляє фото, PostgreSQL зберігає користувачів, сесії,
історію задач і результати. Етап 3: обробка ще синхронна, без фонової черги.

## Структура

```text
backend/
  app/                    # FastAPI, auth, PostgreSQL, задачі, Pillow
  tests/                  # unittest: API та зміна розміру
  requirements.txt
  requirements-dev.txt
frontend/                 # HTML, CSS, JavaScript
Dockerfile
compose.yaml
.env.example              # Приклад налаштувань; справжній .env не потрапляє у Git
```

## Локальний запуск (macOS / VS Code)

Потрібні Python 3.12 і запущений Docker Desktop. Відкрийте папку репозиторію
у VS Code. Один раз створіть `.env` із випадковим паролем PostgreSQL
(команда відмовиться перезаписувати наявний файл):

```sh
python3.12 -c 'import os,secrets; f=os.fdopen(os.open(".env",os.O_WRONLY|os.O_CREAT|os.O_EXCL,0o600),"w"); f.write("POSTGRES_PASSWORD="+secrets.token_hex(32)+"\n"); f.close()'
```

Виконуйте подальші команди з кореня проєкту:

```sh
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements-dev.txt
docker compose up -d --wait db
set -a
source .env
set +a
export DATABASE_URL="postgresql://studio:${POSTGRES_PASSWORD}@127.0.0.1:5433/studio"
python -m uvicorn app.main:app --app-dir backend --reload --host 127.0.0.1 --port 8000
```

Відкрийте у браузері адресу `http://127.0.0.1:8000`, створіть акаунт або увійдіть.
Ім’я: 3–40 латинських літер, цифр, `_` або `-` (регістр не має значення).
Пароль: 10–128 символів. Оберіть фото, задайте рамку й натисніть «Обробити
зображення». Після обробки результат можна завантажити одразу або з «Моєї історії».
Історія зберігається після виходу, перезапуску API та PostgreSQL.
Для зупинки API натисніть Ctrl+C. PostgreSQL слухає лише локальний порт 5433.

## Тести

Тести використовують справжню PostgreSQL. Один раз створіть окрему базу:

```sh
docker compose exec db createdb -U studio studio_test
```

Після запуску PostgreSQL, з активованим venv і завантаженим `.env`:

```sh
export TEST_DATABASE_URL="postgresql://studio:${POSTGRES_PASSWORD}@127.0.0.1:5433/studio_test"
PYTHONPATH=backend python -m unittest discover -s backend/tests -v
```

Набір містить 38 тестів: попередні перевірки зображень плюс реєстрація, вхід,
хешування, відкликання й термін сесій, ізоляція користувачів, історія, завантаження,
видалення, ліміти й одночасний прийом задач. Тести очищають таблиці лише в явно
заданій `TEST_DATABASE_URL`, назва бази має закінчуватися на `_test`.
Не запускайте їх паралельно на тій самій базі. Вони не очищають базу `studio`.

## Docker Compose

Потрібен Docker Desktop із Docker Compose і створений `.env` (див. вище).
Зупиніть локальний Uvicorn, щоб звільнити порт 8000:

```sh
docker compose up --build
```

Застосунок доступний на порту 8000. Зупинка: Ctrl+C, потім `docker compose down`.
Іменований том `postgres_data` зберігає БД. **Не використовуйте `down -v`, якщо
хочете зберегти акаунти та результати.** Зміна пароля в `.env` не змінює пароль
у вже створеній базі: виконайте узгоджену ротацію або використовуйте старий файл.
Docker збирає backend та frontend безпосередньо з цього репозиторію.
У керованому хмарному середовищі з власним TLS-проксі Dockerfile також підтримує
необов'язковий BuildKit secret `proxy_ca` для довіреного CA bundle під час pip install.

## API та зберігання

- `POST /api/auth/register`, `POST /api/auth/login`: JSON `username`, `password`;
  відповідь містить `access_token`, `token_type`, `expires_in`.
- `GET /api/auth/me`, `POST /api/auth/logout`: поточний користувач / вихід.
- `POST /api/images/resize`: multipart `file`, `width`, `height`; повертає PNG і
  заголовок `X-Job-ID`. Потрібен `Authorization: Bearer <access_token>`.
- `GET /api/jobs`, `GET /api/jobs/{id}`: лише власна історія й метадані.
- `GET /api/jobs/{id}/result`: повторне завантаження власного PNG.
- `DELETE /api/jobs/{id}`: видалення завершеної/невдалої задачі разом із результатом.
- `GET /api/health`: перевіряє також доступність БД; `GET /docs`: опис API.

Паролі хешуються Argon2id. Випадкові bearer-сесії діють 24 години; в БД лежать
лише SHA-256-хеші токенів, максимум п’ять активних сесій на користувача.
Браузер зберігає токен в `sessionStorage` поточної вкладки; при виході він
відкликається на сервері. Сервер обмежує входи/реєстрації: 30 запитів на хвилину
на IP і 10 на ім’я. Для майбутнього Nginx потрібно налаштувати довірені proxy IP.
Для публічного розгортання налаштуйте HTTPS; поточні команди — локальна демонстрація.

На старті транзакційно створюється початкова схема (`users`, `sessions`, `jobs`,
`auth_limits`), повторний старт не видаляє дані. Подальші зміни існуючих таблиць
потребуватимуть окремих міграцій. Результати PNG поки зберігаються в `BYTEA`
разом із метаданими — вони спільні для всіх API. Перенесення файлів у спільне
сховище та політика автоматичного очищення — наступні покращення.

## Обмеження та наступні етапи

Backend приймає один файл до 10 MiB, до 12 млн пікселів і 12000 px на сторону.
Результат вписується в рамку до 4096×4096 px без збільшення оригіналу.
Одночасно один процес обробляє максимум два зображення.
На користувача — до двох активних і до 20 збережених задач (невдалі теж
враховуються). Результат — до 20 MiB; старі задачі можна видаляти.
Перевірка лімітів використовує блокування рядка користувача в PostgreSQL,
тому одночасні запити не обходять ліміт.

Наразі працює один API. Статуси: `RUNNING`, `COMPLETED`, `FAILED`. Обробка триває
під час HTTP-запиту. При аварійному завершенні процесу активна задача може лишитися
`RUNNING`; автоматичне відновлення, черга й скасування належать до наступного етапу.
Redis/Celery, прогрес, Nginx і балансування ще не реалізовані.
Для майбутньої демонстрації балансування потрібні окремі перевірки:

1. HTTP-запити через Nginx отримують різні `instance_id` від двох API.
2. Кілька фонових задач виконуються на двох Celery workers; докази — job ID,
   worker ID та журнали. Одна задача автоматично між workers не ділиться.

Обидва API мають використовувати спільні PostgreSQL, Redis і файловий том.
